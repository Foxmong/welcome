# crewAI 기반 앱 개발 조직

[crewAI](https://github.com/crewAIInc/crewAI)를 이용해 만든 **AI 앱 개발 조직**입니다.
프로젝트 요구사항을 한 줄 명령으로 던지면, 4명의 AI 에이전트가 역할을 나눠
기획 → 설계 → 개발 → 리뷰까지 순차적으로 진행합니다.

또한 새 프로젝트를 시작할 때마다 **조직 브랜치와 완전히 격리된 프로젝트
브랜치**가 자동으로 만들어지므로, 조직(베이스) 브랜치는 절대 오염되거나
수정되지 않습니다.

---

## 1. 조직 구성

| 역할 | 하는 일 | 산출물 |
|------|---------|--------|
| PM (프로덕트 매니저) | 요구사항 분석, 기능 목록/우선순위 정리 | `docs/01_기능명세서.md` |
| 소프트웨어 아키텍트 | 기술 스택 선정, 파일/모듈 구조 설계 | `docs/02_기술설계서.md` |
| 시니어 개발자 | 설계에 따라 실제 코드 작성 | `docs/03_구현코드.md` |
| QA 리뷰어 | 명세 대비 구현 검토, 버그/개선점 보고 | `docs/04_리뷰보고서.md` |

## 2. 조직이 돌아가는 방식 (crewAI 핵심 개념)

crewAI는 세 가지 요소로 조직을 구성합니다.

- **Agent(에이전트)** = 조직 구성원. `role`(직책), `goal`(목표),
  `backstory`(경력/성향)를 부여하면 LLM이 그 인격으로 일합니다.
- **Task(태스크)** = 업무 지시서. `description`(할 일),
  `expected_output`(기대 산출물), `output_file`(저장 위치)을 지정합니다.
- **Crew(크루)** = 조직 그 자체. 에이전트들과 태스크들을 묶고,
  `process`(협업 방식)를 정합니다.

이 조직은 `Process.sequential`(순차 프로세스)을 사용합니다.

```
사용자 요구사항
   │
   ▼
[PM] 기능명세서 작성
   │  (명세서가 context로 자동 전달)
   ▼
[아키텍트] 기술설계서 작성
   │  (명세서 + 설계서 전달)
   ▼
[개발자] 코드 작성
   │  (명세서 + 코드 전달)
   ▼
[QA] 리뷰 보고서 작성
   │
   ▼
격리된 프로젝트 브랜치에 커밋
```

핵심은 각 Task에 `context=[이전_task]`를 지정하면 **앞 사람의 산출물이
뒷 사람에게 자동으로 전달**된다는 점입니다. 실제 회사에서 기획서가
개발팀으로 넘어가는 것과 동일한 구조입니다.

> 참고: crewAI에는 `Process.hierarchical`(계층 프로세스)도 있습니다.
> 매니저 에이전트가 팀원에게 업무를 위임/조율하는 방식으로,
> 조직이 커지면 이 방식으로 확장할 수 있습니다.

## 2-1. 메시지 전달(handoff) 과정 확인하기

"누가 무엇을 만들어서 다음 사람에게 넘겼는지"를 실행 중/실행 후에 눈으로
확인할 수 있습니다.

- **실행 중**: 각 에이전트가 작업을 끝낼 때마다 터미널에 다음과 같은 로그가
  즉시 출력됩니다.

  ```
  [핸드오프 2] '소프트웨어 아키텍트' 작업 완료 → 다음 단계로 결과 전달됨
             (전체 내용: .../logs/handoff.md)
  ```

  (이 외에도 `verbose=True` 설정으로 각 에이전트의 사고 과정과 세부 실행
  로그가 함께 출력됩니다.)

- **실행 후**: 프로젝트 폴더의 `logs/handoff.md` 파일을 열면, PM → 아키텍트
  → 개발자 → QA 순서로 각 단계가 언제 끝났고 어떤 내용을 다음 사람에게
  넘겼는지가 시간순으로 정리되어 있습니다. 각 단계마다 다음 정보가 기록됩니다.

  | 항목 | 설명 |
  |------|------|
  | 몇 단계 / 어떤 에이전트 | 예: "2단계 완료 — 소프트웨어 아키텍트" |
  | 시각 | 해당 단계가 끝난 시각 |
  | 태스크 | 어떤 업무였는지 |
  | 전달 내용 미리보기 | 다음 에이전트에게 그대로 전달되는 실제 텍스트 |

이 기능은 `handoff_logger.py`가 crewAI의 `task_callback`(태스크 완료 시
호출되는 콜백)을 이용해 구현되어 있습니다. `context=[이전_task]`로 연결된
태스크는 이 시점의 출력 전체를 다음 에이전트의 프롬프트에 자동으로
포함시키는데, 로거는 그 "넘어가는 순간"을 그대로 캡처해 기록만 남깁니다 —
즉 실제 동작에는 전혀 개입하지 않는 순수 관찰(observability) 기능입니다.

## 3. 브랜치 격리 — 조직 브랜치는 절대 안 바뀝니다

**가능합니다.** 이 저장소는 `git worktree`를 이용해 3중으로 격리합니다.

1. **브랜치 격리** — 새 프로젝트마다 조직 브랜치에서 `project/<이름>`
   브랜치를 새로 분기합니다. 이후 두 브랜치는 완전히 독립적입니다.
2. **디렉터리 격리** — worktree가 프로젝트 브랜치를 **별도 폴더**
   (`.projects/<이름>/`, `.gitignore` 처리됨)에 체크아웃합니다. AI가 만드는
   모든 파일은 그 폴더 안에만 생기고, 조직 브랜치가 추적하는 파일은
   하나도 안 바뀝니다.
3. **커밋 격리** — 산출물 커밋은 프로젝트 브랜치에만 쌓입니다.
   조직 브랜치의 커밋 이력은 그대로 보존됩니다.

```
저장소 구조 (프로젝트 2개 진행 중일 때):

welcome/                       ← 조직 브랜치 (읽기 전용처럼 보존됨)
├── app_dev_org/               ← 조직 정의 코드
├── .projects/                 ← 프로젝트 전용 폴더 (.gitignore 처리, 자동 생성)
│   ├── todo-app/              ← project/todo-app 브랜치의 worktree
│   │   └── docs/01_기능명세서.md ...
│   └── chat-app/              ← project/chat-app 브랜치의 worktree
│       └── docs/...
└── ...
```

프로젝트 브랜치의 결과물이 마음에 들면 그때 PR/머지로 가져오면 되고,
마음에 안 들면 브랜치를 통째로 버리면 됩니다. 어느 쪽이든 조직 브랜치는
영향을 받지 않습니다.

## 4. 설치

```bash
cd app_dev_org
python3 -m venv ../.venv
../.venv/bin/pip install -r requirements.txt

# API 키 설정 (crewAI는 LLM API 키가 필요합니다)
cp .env.example .env
# .env 파일을 열어 OPENAI_API_KEY 입력
```

## 5. 사용법

```bash
cd app_dev_org

# 새 프로젝트 명령 → 격리 브랜치 생성 → 조직 가동 → 결과 커밋
../.venv/bin/python main.py new "todo-app" "간단한 할 일 관리 웹앱. 추가/완료/삭제 기능 필요."

# 진행 중인 프로젝트 브랜치 목록
../.venv/bin/python main.py list

# 프로젝트 작업 폴더 정리 (브랜치는 보존)
../.venv/bin/python main.py clean "todo-app"
```

실행이 끝난 뒤 조직 브랜치에서 `git status`를 치면
`nothing to commit, working tree clean` — 즉 아무것도 안 바뀐 것을
직접 확인할 수 있습니다.
